# AI Catalog

`/ai-catalog.json` — пользовательский UTF-8 JSON-каталог Laser Tech Service для собственных интеграций и систем, явно поддерживающих этот формат. Это не стандарт Google или OpenAI; наличие файла не гарантирует индексацию или использование AI-системами.

## Команды

```sh
python3 scripts/build-ai-catalog.py
python3 scripts/build-ai-catalog.py --check
python3 scripts/check-ai-catalog.py
python3 scripts/build-site.py
```

Первая команда генерирует каталог. `--check` проверяет структуру, источники и актуальность без записи; возвращает ненулевой код для устаревшего каталога. `check-ai-catalog.py` дополнительно проверяет изменения цены, отсутствие перевода, удаление и переименование страницы, дубли ID, стабильность JSON и отсутствие записи в режиме проверки.

## Источники и публикация

Используется `discover()` из существующего `scripts/build-ai-search.py`: список канонических HTML из `sitemap.xml`, PL/RU, JSON-LD, метаданные, дерево HTML. Отдельной ручной базы бизнес-данных нет. Sitemap в текущем проекте поддерживается вместе с контентом; собственного генератора sitemap и GitHub Actions нет.

Включение в sitemap означает включение в статическую публикацию, а не подтверждение доступности на production. Страницы вне sitemap, включая технические, legacy-дубли и несуществующие переводы, не сканируются. Если sitemap содержит отсутствующий файл, noindex или несовпадающий canonical, сборка останавливается: ошибка источника не маскируется пропуском записи. При удалении или изменении URL необходимо обновить sitemap и языковые связи.

`netlify.toml` задаёт сборку `python3 scripts/build-site.py` и публикацию корня. Сборка запускает существующие генераторы карточек и AI/Markdown, затем AI Catalog и проверки сайта. Каталог обновляется при каждом таком build, включая изменения текста, цены и состава опубликованных страниц. Коммитов и циклов автоматических коммитов нет. При другом хостинге нужно запускать ту же команду перед публикацией; ручная загрузка без build ничего не генерирует.

Точный путь `/ai-catalog.json` получает `application/json; charset=utf-8`, `nosniff` и обязательную проверку свежести кэша. Файл не включён в sitemap как HTML, не добавлен в интерфейс и не получил фиктивную Schema.org-разметку. `robots.txt`, `llms.txt`, SEO HTML и прежняя Markdown-документация не изменяются генератором каталога.

## Структура версии 1.0

- `schema_version`, `catalog_type`, `generated_at`: версия формата и время фактического изменения результата. При неизменном содержимом сохраняется прежняя временная метка и побайтово одинаковый JSON. Проверка существующего `generated_at` требует корректного ISO-8601.
- `business`: подтверждённые сведения из LocalBusiness на польской главной: имя, URL, телефон, email, адрес, основной город, территория обслуживания, специализация и sameAs. `source_url` указывает источник. Данные не переводятся и не дублируются вручную.
- `languages`: поддерживаемые исходные языки.
- `services`: только отдельные посадочные страницы с Service JSON-LD и компонентом service-landing. Каталоги и прайс не являются отдельными услугами. Взаимные PL/RU hreflang объединяются в одну запись; отсутствующий перевод не создаётся. `localizations` содержит заголовок, описание, URL, цену и направления работ на языке страницы. `equipment_category` — нормализованная категория из явных терминов заголовка; при отсутствии однозначного соответствия null.
- `starting_price`: только явно опубликованное «od/от … zł» в `.service-price`; валюта PLN, тип starting_from, исходный текст, URL и примечания hero. Другие суммы из прайса, FAQ, выезда или навигации не подменяют стартовую цену. В частности 800 zł за начальный сервис диодов не означает включённый новый модуль.
- `available_work`: H3 внутри раздела с заголовком «Co obejmuje», «Zakres» или «Что входит». Симптомы и FAQ не используются как перечень работ.
- `articles`: одна запись на существующую языковую страницу. Заголовок/H1, description, язык/canonical, категория статьи или schema keywords/articleSection, даты только из Article/BlogPosting. `related_services` — ссылки на реальные посадочные внутри main; это явная связь страниц, а не автоматически угаданная тематика.
- `case_studies`: одна запись на исходную страницу. Подписанные поля `.case-info__item` дают город/место и тип оборудования; schema about сохраняется отдельно как `equipment`. Неисправность, работы и результат извлекаются дословно из абзацев/списков после соответствующих H2/H3. Если конструкция страницы не позволяет надёжное извлечение, значение null или пустой список. Город из «Lokalizacja» может включать страну: исходная формулировка сохраняется.
- `resources`: существующие sitemap, llms и соответствия canonical → Markdown.

ID строятся из типа записи и канонического пути: стабильны при изменении текста, цен и дат. При смене канонического URL меняется ID; потребителям нужно учитывать миграции URL. Записи и языки сортируются для стабильного результата.

## Проверки и текущий охват

На момент реализации: 8 услуг / 16 языковых посадочных, 42 статьи, 44 кейса. Все статьи получили тематику. Не подтверждены даты публикации у 8 статей и изменения у 2; они не создаются искусственно.

Пустые поля среди 44 кейсов: город — 29; тип оборудования — 30; описание неисправности — 8; выполненные работы — 22; результат — 26. Это ограничения консервативного извлечения неоднородной старой разметки, не утверждение об отсутствии сведений в свободном тексте. Полный canonical и description доступны для обращения к оригиналу.

Валидатор проверяет уникальность ID, покрытие статей/кейсов, существование локальных ресурсов, HTTPS, язык, соответствие опубликованной цене. Внешние социальные URL берутся из сайта; их сетевой доступ не проверяется. Production-ответы Netlify можно подтвердить только после отдельной публикации. Добавление конфига не выполняет deploy.
